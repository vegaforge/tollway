# Receipt v2

A v2 receipt binds the exact offer the payer accepted (by hash), the HTTP
method of the paid request, and an optional expiry, so a receipt proves
what was bought and not only which URL. The verifier accepts v1 and v2.

`receiptBodySchema` is now a union discriminated on `version`:
`receiptBodyV1Schema` is unchanged byte-for-byte, and the new
`receiptBodyV2Schema` adds:

- `offerHash`: base64url SHA-256 of the RFC 8785 canonical bytes of the
  offer the payer accepted. The hash input includes `models` (ordered),
  `facilitatorUrl`, `mppSessionSupported` and `quote` in addition to
  `resource`, `amount`, `asset`, `payTo` and `network`. A new exported
  `hashOffer(offer)` is the only way the gate and verifiers compute it.
- `method`: a non-empty string. Convention is the uppercase HTTP method
  (`GET`, `POST`, ...) for HTTP gates and any stable identifier for
  non-HTTP gates. A receipt for `GET /x` no longer unlocks `POST /x`.
- `expiresAt`: optional ISO 8601 timestamp strictly after `issuedAt`. A
  receipt without `expiresAt` never expires.

`buildReceipt` returns v2 when given both `offerHash` and `method`, v1
when given neither, and throws `invalid-receipt` when given only one, so
a v2 field is never dropped silently.

`verifyReceipt(candidate, verifier, { now? })` accepts an optional `now`
in ms and rejects a v2 receipt whose `expiresAt` is at or past that time
with the distinct reason `"receipt expired"`. The signature is checked
first, so that reason is only given for a receipt the trusted key really
signed. `verifyReceipt` never throws: a signature that is not base64url,
or a verifier that throws, is an invalid result with a reason.

The gate issues v1 receipts until the operator sets `receiptVersion: 2`
in the `createPaywall` dependencies. An older process reading a v2 cache
entry treats it as a miss and calls `/settle` again, so the switch is
explicit. The safe order: deploy this version everywhere with
`receiptVersion` unset, wait until no older process serves traffic or
shares the cache, then set `receiptVersion: 2`. Cached v1 receipts keep
being served after the switch. A cached v2 receipt is only served when
its `offerHash` and `method` match the request's offer, on top of the
six fields a v1 receipt is bound by, so a receipt for offer A is never
served for offer B with the same price and resource. The offer is hashed
once per fresh settlement, and only in v2 mode.

`docs/receipt-format.md`, the receipts page of the docs site and the
dashboard's receipt detail view show the v2 fields.
