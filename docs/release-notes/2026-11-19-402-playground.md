# In-browser 402 playground

`/docs/playground` (sidebar section "Tools") has a Decode tab and an Encode
tab. Decode takes a `PAYMENT-REQUIRED`, `PAYMENT-SIGNATURE`,
`PAYMENT-RESPONSE` or `TOLLWAY-RECEIPT` value, works out whether it is
base64 or base64url, identifies the shape (x402 `PaymentRequired`,
`PaymentPayload` or `SettleResponse`, or Tollway's `PaymentOffer` or signed
receipt), validates it and explains every field. A Tollway receipt can be
verified against a pasted public key, JWKS document or `{ keyId, publicKey }`
object with `verifyReceipt` from `@vegaforge/tollway-core`. A
`PAYMENT-SIGNATURE` is summarised (network, payer, amount) and the page says
to treat it as sensitive. Encode builds a challenge from a form and prints it
in both encodings. Closes #258.

Nothing pasted leaves the page: there is no `fetch`, no analytics, and share
links are opt-in and live only in the URL fragment. A `PAYMENT-SIGNATURE` is
never put in a link.

Technical shape. The logic lives in `apps/web/src/lib/playground/`
(encoding, shapes, explain, decode, encode, verify, signature, xdr, share)
and is tested in node; the component is tested in jsdom with `fetch`,
`XMLHttpRequest`, `sendBeacon` and `WebSocket` replaced by spies. Fixtures
come from the real encoders: `@x402/core/http` for the x402 shapes and
`encodeHeader` from `@vegaforge/tollway-server` (a dev dependency) for the
Tollway shapes.

Choices the issue left open:

- `@x402/core` has no `SettleResponse` schema and core has no `PaymentOffer`
  schema, so both are written out in `shapes.ts` with compile-time checks
  that they match the package types. No package API changed.
- A single header value is capped at 16 KiB, Node's default limit for all
  headers of a request.
- The payer of an x402 Stellar payment is inside the signed transaction, so
  the summary decodes that transaction with `@stellar/stellar-base` 15.0.0
  (already in the lockfile), loaded only when a signature is decoded.
- Share links exist and are opt-in ("Create share link"); restoring a broken
  link says so instead of guessing.
- The encode form's network is Tollway's `testnet` or `mainnet`, mapped to
  `stellar:testnet` / `stellar:pubnet` exactly as `createHttpFacilitator`
  does; `maxTimeoutSeconds` uses its default of 60.

Bundle, measured with `next build` on the gzip size of the scripts each
prerendered page loads: every docs page before this change loaded 827 KB
raw / 263 KB gzip; after it, 832 KB / 264 KB. The playground itself
(`next/dynamic`, client only) is a separate 447 KB / 107 KB chunk loaded on
`/docs/playground` only, and `@stellar/stellar-base` is a further
440 KB / 113 KB chunk loaded only when a signed payment is decoded.

`apps/web/netlify.toml` now rebuilds the site when `packages/core` changes.
