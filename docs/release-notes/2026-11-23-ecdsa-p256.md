# ECDSA P-256 receipt signing

Receipts can now be signed with ECDSA P-256 (`ES256`) in addition to
Ed25519. Many managed-key services and HSM fleets offer P-256 but not
Ed25519, and the receipt format should not force a deployment to keep
its receipt key outside the HSM for that reason.

The new `EcdsaP256Signer` uses WebCrypto's `ECDSA` with
`namedCurve: "P-256"` and SHA-256. It generates keypairs (the private
key is not extractable), imports PKCS#8 DER (`fromPkcs8`, bytes or
base64url) and private JWKs (`fromJwk`, with a cross-check that the
declared public half matches the private material), and exports its
public JWK in the shape a key-set document expects. The wire format is IEEE P1363 (`r || s`, 64 bytes)
base64url; signatures with `s > n/2` are normalised to `n - s` at
signing and rejected at verifying, so each receipt has one valid
encoding and ECDSA's malleability window is closed.

A new `EcdsaP256Verifier` covers the single-trusted-key case, mirroring
`Ed25519Verifier`. Most callers use `createKeySetVerifier` instead,
which now accepts `kty: "EC", crv: "P-256"` entries alongside
`kty: "OKP", crv: "Ed25519"`. The key-set verifier binds each key
record to the algorithm declared in its `alg`: a receipt whose
`signature.algorithm` disagrees with the record is rejected, so an
Ed25519 key can never check an ES256 signature or the other way
round. `Ed25519` (the pre-#167 receipt spelling) and `EdDSA` (the JWK
JOSE name) are treated as the same algorithm.

A `derToP1363(der)` helper is exported for KMS-backed signers whose
wire format is ASN.1 DER, with `normaliseLowS` to move `s` into the low
half. The parser is strict: it rejects trailing bytes, non-minimal
lengths and integer encodings, negative integers, and an r or s that is
zero, longer than 32 bytes, or not below the P-256 order. Every DER
failure throws the new code `invalid-signature-encoding`.

The algorithm identifiers and the P-256 constants live in one module,
`algorithms.ts`, and `RECEIPT_ALGORITHMS` (`Ed25519`, `EdDSA`, `ES256`)
is the registry every verifier reads. A receipt with an unknown
algorithm, `none` included, fails verification without throwing.

Interop is tested against an independent implementation: the RFC 6979
appendix A.2.5 signature verifies once normalised (and its high-S form
is refused), Node's `crypto` DER signatures verify after conversion, and
Node's `crypto` accepts Tollway's signatures. The published vectors gain
verify-only ES256 cases signed with the RFC 6979 test key.

Existing Ed25519 receipts behave exactly as before. `Ed25519Verifier`
also accepts `EdDSA`, the JOSE name for the same algorithm, and returns
false instead of throwing for a malformed trusted key.
