The observability hub collects one `PaymentMetric` per measured payment and answers questions about them: how much was spent, on which model, in which asset, how often payments failed, and how long they took. It also delivers webhook events (`receipt.created`, `channel.opened`, `channel.closed`, `budget.warning`, `anomaly.detected`, `sponsor.low_balance`) to local handlers and HTTP subscribers.

```ts
import { createObservabilityHub } from "@vegaforge/tollway-observability";

const hub = createObservabilityHub();

hub.record({
  payer: "GAGENT...",
  payee: "GSERVICE...",
  model: "x402",
  amount: "10000", // 0.001 USDC: 7 decimals, integer string in the smallest unit
  asset: "USDC:GA5Z...",
  latencyMs: 182,
  outcome: "settled", // or "failed" / "skipped"
  at: "2026-11-19T10:04:31.000Z",
});
```

Metrics are held in memory by the hub. Every amount, in and out, is an integer string in the asset's smallest unit, added with `bigint`.

## Querying a time series

`hub.timeseries` cuts a time range into buckets and returns, for each bucket, one row per model and asset:

```ts
const series = hub.timeseries({
  from: "2026-11-19T00:00:00Z",
  to: "2026-11-20T00:00:00Z",
  bucket: "1h", // "1m" | "5m" | "1h" | "1d"
  groupBy: "payee", // optional: "model" (default), "payee" or "payer"
  model: "x402", // optional filters, as in summarize: payer, payee, model
});

for (const bucket of series.buckets) {
  for (const row of bucket.rows) {
    // row.model, row.asset, row.payee
    // row.amount   settled amount, integer string
    // row.settled, row.failed, row.skipped
    // row.latencyMs  { p50, p95, p99 } or null when the row is empty
  }
}
```

How the range and the buckets behave:

- **Both ends are required** and must be ISO 8601 timestamps with `Z` or an explicit offset such as `+02:00`. A timestamp without a zone is rejected, because it would be read in the server's local time.
- **The range is half-open**, `[from, to)`: a metric exactly at `to` belongs to the next range. This differs from `summarize`, whose `to` is inclusive. A day of hourly buckets is `from: "...T00:00:00Z"` to the next midnight, which is exactly 24 buckets.
- **Buckets are aligned to UTC.** Each bucket starts at a whole multiple of its width counted from the Unix epoch, so `1h` buckets start on the UTC hour and `1d` buckets at UTC midnight, wherever the server runs. The first bucket starts at `from` rounded down; metrics before `from` are still left out of it. `series.from` and `series.to` report the rounded range.
- **Buckets are contiguous.** Every bucket in the range is returned, in time order, including empty ones. Every group (model and asset, plus payee or payer when asked) seen anywhere in the range has a row in every bucket, in the same order; in a bucket where it had no metrics, the row has zero counts, `amount: "0"` and `latencyMs: null`.
- **Assets are never added together.** `asset` is part of every row's key.
- **Only settled payments move money.** `amount` adds the row's `settled` metrics only. `settled`, `failed` and `skipped` count each outcome.
- **Bad data is an error, not a gap.** A recorded metric in the range with an unparseable `at`, a settled `amount` that is not an integer string, or a negative or non-finite `latencyMs` makes the query throw a `TollwayError` with code `invalid-metric`. A malformed query throws `invalid-metrics-query`.

### Size limits

A query that would produce more buckets than `maxTimeseriesBuckets` (default 10 080, seven days of one-minute buckets), or more rows than `maxTimeseriesRows` (default 200 000, counted as buckets times groups), throws `MetricsQueryTooLargeError` (code `metrics-query-too-large`) before allocating the result. The error carries `limit` (`"buckets"` or `"rows"`), `requested` and `maximum`. Both limits are hub options:

```ts
const hub = createObservabilityHub({ maxTimeseriesBuckets: 1440, maxTimeseriesRows: 50_000 });
```

## How latency percentiles are computed

`p50`, `p95` and `p99` use the **nearest-rank** method on the exact latency samples of the row: sort the `n` samples in ascending order, and the p-th percentile is the sample at 1-based rank `ceil(p / 100 * n)`.

- Every reported value is a latency that was actually recorded. Nothing is interpolated or estimated.
- With 4 samples `[1, 10, 20, 900]`, p50 is rank 2 (`10`), and p95 and p99 are both rank 4 (`900`). With few samples the high percentiles equal the maximum, which is the honest answer.
- `p50 <= p95 <= p99` always holds.
- Samples come from every metric in the row whatever its outcome, so a slow failure shows up in the latency of the model that produced it.

The helper is exported as `nearestRankPercentile(sorted, p)` for callers that need the same method elsewhere.

### Per store

| Store | Bucketing and counts | Percentiles |
| ----- | -------------------- | ----------- |
| In-memory hub (the only store today) | Computed in process | Exact nearest rank over every sample in the row |

There is no SQL store in `@vegaforge/tollway-observability` yet; it is tracked in [#217](https://github.com/vegaforge/tollway/issues/217). When it lands, the plan is to push bucketing (`floor(epoch_ms / width) * width`) and the per-outcome counts and settled sums into `GROUP BY` queries, keep the half-open range and UTC alignment above, and either compute percentiles exactly in SQL where the database has a nearest-rank aggregate (PostgreSQL's `percentile_disc` is one) or fetch the row's latency samples and apply the same nearest-rank method in process (SQLite has no percentile aggregate). This table will then list the method each store uses.

## Spend summaries

`hub.summarize(query?)` returns one flat summary over the whole window. Use `byAsset` for amounts: it holds the amount per asset and never adds different assets together.

`totalAmount`, `byModel`, `byPayer` and `byPayee` are **deprecated**. They add amounts across assets, so they only make sense when the window holds a single asset, and like `byAsset` they include failed and skipped metrics. They keep their values for existing callers. For settled-only amounts, per-model or per-counterparty amounts in one asset, an outcome split, or latency, use `timeseries` and add up the rows you need.

## Exports and webhooks

`hub.export("json" | "csv", query?)` serializes the matching metrics. `hub.on(event, handler)` and `hub.addWebhook({ url, events?, secret? })` subscribe to webhook events, which `hub.emit(event)` delivers with retries and reports in a `DeliveryReport`.

Every event carries a stable `id` assigned at emit time. Each request includes `Tollway-Event-Id`, and a subscription with a `secret` also gets a `Tollway-Signature` header that covers the exact body. Export `verifyWebhookSignature` from the package to check it on the receiving side, rejecting forged bodies and replayed timestamps.

### Durable delivery

Pass an `outbox` to `createObservabilityHub` to persist each delivery instead of POSTing inside `emit`. `createSqliteWebhookOutbox({ filename })` survives a restart; `createMemoryWebhookOutbox()` keeps rows in process for tests. Call `hub.startDispatcher()` to deliver with jittered exponential backoff under a lease, and `hub.stop()` to wait for in-flight attempts on shutdown. With an outbox, `emit` never rejects: a row that cannot be written is listed in the report's `failures`.

Delivery is **at-least-once**, and ordering is not guaranteed. Receivers dedupe on `Tollway-Event-Id`. `Tollway-Delivery-Id` names the delivery row: it is the same across retries of that row and new only when the row is enqueued or replayed. A delivery that exhausts `maxAttempts` (16 by default, retried over about 2 to 4 hours) moves to a dead-letter state: list it with `outbox.listDeadLetters()` and re-enqueue it once with `outbox.replay(deliveryId)`, which resets attempts and issues a fresh delivery id. Delivered rows are purged after `dispatcher.deliveredRetentionMs` (24 hours by default). Rows store the subscription id, never the secret, so the same subscriptions must be registered again after a restart.

The full workflow, including the header format, leases, retention and a receiver example, is in [`docs/webhook-delivery.md`](https://github.com/vegaforge/tollway/blob/dev/docs/webhook-delivery.md).

## Fee-sponsor balances

`createSponsorMonitor` from `@vegaforge/tollway-server` observes the native XLM
balance of configured Stellar accounts. It never funds, tops up, transfers from,
or signs for an account. The balance includes the account reserve; it is not an
estimate of spendable funds or the number of payments remaining.

```ts
import { createSponsorMonitor } from "@vegaforge/tollway-server";
import { createObservabilityHub, renderFeeSponsorMetrics } from "@vegaforge/tollway-observability";

const hub = createObservabilityHub();
const monitor = createSponsorMonitor({
  network: "testnet",
  accounts: [process.env.FEE_SPONSOR_ACCOUNT!], // the actual G... fee payer
  thresholdStroops: "100000000", // 10 XLM
  hysteresisStroops: "10000000", // re-arm strictly above 11 XLM
  intervalMs: 60_000,
  sink: hub,
});

hub.on("sponsor.low_balance", (event) => console.warn(event.data));
await monitor.start(); // immediate reading, then an unref'd timer
// When shutting down:
await monitor.stop(); // waits for an in-flight read

// A string in Prometheus text exposition format 0.0.4:
const body = renderFeeSponsorMetrics(hub);
```

For a single reading without a timer, use `await monitor.poll()`. Concurrent
calls share the current poll, and the next timer starts only after the entire
poll completes. `start()` and `stop()` can be called repeatedly. Background
discovery and sink errors go to `onError`, defaulting to `console.error`.
Read failures become stale readings and polling continues.

Horizon responses are schema-checked. Decimal XLM is converted to integer
stroops without floating point (1 XLM = 10,000,000 stroops). All comparisons
use `bigint`. A balance below the threshold emits one `sponsor.low_balance`
event with `account`, `network`, `balanceStroops`, `thresholdStroops` and
`hysteresisStroops`. It re-arms only after a successful reading strictly above
threshold plus hysteresis. A read failure neither alerts nor re-arms.

`hub.getSponsorReadings()` returns the latest attempt for each network/account.
A failed attempt has `stale: true`, an `error`, and no current `balanceStroops`;
it replaces any previous successful reading. Each reading has an ISO timestamp
`at`. Staleness records the last attempt's outcome; readings do not automatically
expire. Use `at` for an application-defined age check, including when a stopped
monitor leaves the metrics endpoint running. Prometheus `up` detects a failed
scrape of the service endpoint.

### Account discovery and OpenZeppelin

Omit `accounts` and pass `facilitator` to seed the list from its schema-checked
`/supported` signers for `stellar:testnet` or `stellar:pubnet`. Discovery is
frozen after the first successful lookup; recreate the monitor when accounts
change. Explicit `accounts` always overrides discovery, and an empty explicit
list disables observation. Duplicate accounts are read once.

Signer addresses are not proof of who pays transaction fees. Confirm the actual
fee payer with your facilitator operator before enabling discovery. OpenZeppelin
Channels' testnet `/supported` endpoint returned HTTP 401 without credentials
when checked for this change, so its signer-to-sponsor mapping was not verified.
If the actual sponsor is absent, configure its
G... account explicitly. Service-sponsored MPP charges also need their actual
fee-payer account configured explicitly. Missing signers for the requested
network is an error requesting explicit configuration, never a successful empty
monitor.

### Prometheus gauges

The payment exporter tracked in [#218](https://github.com/vegaforge/tollway/issues/218)
is separate work. `renderFeeSponsorMetrics(hub)` supplies the sponsor portion for
that exporter, or can be mounted on its own in an authenticated metrics route:

```ts
app.get("/metrics", (_req, res) => {
  res.setHeader("Content-Type", "text/plain; version=0.0.4");
  res.send(renderFeeSponsorMetrics(hub));
});
```

| Metric | Type | Labels | Meaning |
| --- | --- | --- | --- |
| `tollway_fee_sponsor_balance_stroops` | gauge | `account`, `network` | Latest native XLM balance; omitted when stale |
| `tollway_fee_sponsor_balance_stale` | gauge | `account`, `network` | 1 when the last read failed, otherwise 0 |

Account labels are bounded by the configured sponsor list and expose those
addresses to scrapers. Protect the metrics route. The renderer preserves integer
text, but Prometheus stores float64 samples and can round amounts above 2^53.
Use these gauges for monitoring, never accounting.

The demo prints one reading before serving in live mode. Set
`FEE_SPONSOR_ACCOUNTS` to a comma-separated list of actual sponsor G... accounts
when discovery is unsuitable. `FEE_SPONSOR_THRESHOLD_STROOPS` defaults to
`10000000` (1 XLM); choose a threshold for your workload. Mock mode injects an
offline fake reader and prints `1000000000` stroops. The demo does not start a
background timer; library services should call `start()` and stop on shutdown.
