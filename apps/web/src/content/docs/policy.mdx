Policy is data, not code: a small declarative schema the policy engine enforces across every settlement model. Enforcement applies the same way whether the payment runs through x402, MPP charge, or MPP channel, because policy sits above the router.

## The schema

```ts
type Policy = {
  $schema?: string; // optional; lets an editor find the JSON Schema, ignored by the engine
  policyVersion: 1; // required; 0 (unversioned) is migrated on parse
  mode?: "enforce" | "dry-run"; // default "enforce"
  budgets?: {
    daily?: string;   // spend ceiling per UTC day, integer string in smallest unit
    total?: string;   // lifetime ceiling for this policy
  };
  perService?: Record<string, {
    cap?: string;                                       // lifetime
    dailyCap?: string;                                  // UTC-day
    window?: { windowSeconds: number; cap: string };    // sliding window
  }>;
  perResource?: Record<string, {
    cap?: string;
    dailyCap?: string;
    window?: { windowSeconds: number; cap: string };
    match?: "exact" | "prefix";                         // default "exact"
  }>;
  perModel?: Partial<Record<SettlementModel, {
    enabled?: boolean;
    minChannelDeposit?: string;
  }>>;
  rateLimit?: {
    requestsPerMinute?: number;                         // shorthand: one 60s window
    windows?: { windowSeconds: number; limit: number }[]; // all apply together
    count?: "settlements" | "attempts";                 // default "settlements"
    scope?: "global" | "per-counterparty";              // default "global"
    perCounterpartyKeyLimit?: number;                   // default 1024
  };
  anomaly?: {
    maxSpendPerMinute?: string;
    adaptive?: {
      kind: "ewma";
      smoothing: { numerator: string; denominator: string };
      sensitivity: { numerator: string; denominator: string };
      warmupPeriods: number;
      scope?: "asset" | "asset-payee";
      maxBaselineGrowthPerMinute?: string;
    };
  };
};
```

Every amount is an integer string in the asset's smallest unit, the same convention used on the canonical receipt. That is what lets the engine compose with bigint arithmetic and keep 64-bit amounts exact. Every object in the schema is strict: an unknown key such as `budgets.dialy` is an error, not a rule that silently enforces nothing.

## Versioning, validation and policy files

`policyVersion` is required in a policy file. Version `1` is the current shape. A document without the field (and a document with `"policyVersion": 0`) is the legacy, unversioned shape from earlier releases; it is migrated to version 1 by adding the field, then validated. Any other version is refused with the supported versions in the message, so a newer file fails loudly instead of being half-enforced by an older engine.

Parse an external policy with `parsePolicy`, which returns every issue with its field path instead of throwing:

```ts
import { parsePolicy } from "@vegaforge/tollway-core";

const result = parsePolicy(JSON.parse(file));
if (!result.ok) {
  for (const issue of result.issues) {
    console.error(`${issue.path.join(".")}: ${issue.message}`);
  }
} else {
  const policy = result.policy; // typed, current version
}
```

The engine validates at construction. A bad amount, a negative rate, an unknown key, or an unsupported `policyVersion` throws `PolicyValidationError` (a `TollwayError` with code `invalid-policy`) from `createPolicyEngine`, listing every issue. Nothing is discovered on the first payment.

In Node, load a JSON policy file with the separate Node-only entry point, which keeps `node:fs` out of the edge-safe main entry:

```ts
import { loadPolicyFile, PolicyLoadError } from "@vegaforge/tollway-core/policy-loader";

try {
  const policy = await loadPolicyFile("./tollway-policy.json");
} catch (error) {
  if (error instanceof PolicyLoadError) {
    // error.kind is "read", "json" or "validation"; error.issues names fields.
  }
}
```

### Editor autocompletion

The schema is published as JSON Schema, with a description on every field, so an editor can validate a policy file and explain each field while you write it. The file is generated from `policySchema`, and the test suite fails when it is stale.

There are two ways to point an editor at it. The first is a `$schema` line in the policy file, which the engine accepts and ignores:

```json
{
  "$schema": "https://raw.githubusercontent.com/vegaforge/tollway/dev/packages/core/schema/policy.schema.json",
  "policyVersion": 1,
  "budgets": { "daily": "1000000000" }
}
```

The second works offline and matches the version you installed: point the editor at the copy inside the package, `node_modules/@vegaforge/tollway-core/schema/policy.schema.json`. In VS Code, add it under `json.schemas` in your settings, with `fileMatch` set to your policy file's name. Code can also import it as `@vegaforge/tollway-core/schema/policy.schema.json`.

## What each field does

**`mode`** is `enforce` unless you set it. In `enforce`, a failing rule blocks the payment. In `dry-run`, every rule is evaluated the same way, spend is recorded the same way, and the payment is allowed; the decision trace marks what enforce mode would have blocked. See "Dry-run and shadow policies" below. An unknown mode is refused at construction with a `PolicyValidationError`.

**`budgets.daily`** is the per-UTC-day ceiling. The engine resets at the day boundary derived from the configured clock.

**`budgets.total`** is the lifetime ceiling for this policy. Useful for a fixed credit allocation.

**`perService`** lets the agent cap exposure to a single counterparty independently of the global budget. The key is the payee address (or service id). Each entry carries up to three ceilings: `cap` is a lifetime cap (never resets), `dailyCap` resets at the same UTC midnight as `budgets.daily`, and `window = { windowSeconds, cap }` is a sliding rolling-window cap (for example 5 USDC per hour). All three count only recorded, settled spend and are tracked per `(payee, asset)`.

**`perResource`** mirrors the same three ceilings (`cap`, `dailyCap`, `window`) but keyed off the resource identifier the receipt carries. The identifier is compared as a plain string, so it includes any query string: `/api/quotes?pair=usd` and `/api/quotes` are different resources. An entry matches the resource exactly by default. Setting `match: "prefix"` lets one entry cover every resource that starts with its key, and the comparison is character by character, so the prefix `/api` also matches `/apix`. End a prefix with `/` to cover one path segment. No regex or glob is evaluated from config.

Every entry that matches a resource applies, and every one of them is charged when a payment is recorded. A narrower entry can tighten a broader one but never lift it: with `/api/` capped at 150 and `/api/quotes/` at 10000, total spend under `/api/` still stops at 150.

Rolling-window accounting is approximate on purpose: a shared `RollingSum` accumulator bucketises time (default `windowMs / 60`), so memory per key is bounded to at most `ceil(windowMs / bucketMs) + 1` entries regardless of traffic. The accumulator may over-count by at most one bucket's worth of spend at the window edge and never under-counts, so a cap on top of it fails closed. Idle keys are evicted once their window drains. `windowSeconds` must be a whole number of seconds, at least 1, and every cap must be a base-unit integer string. `createPolicyEngine` refuses a policy that breaks either rule with a `PolicyValidationError` naming the field, for example `perService.GPAYEE.window.windowSeconds`.

Examples of each cap kind:

```ts
const policy: Policy = {
  policyVersion: 1,
  perService: {
    // Lifetime: never more than 50 USDC to this payee, ever.
    GPAYEE: { cap: "500000000" },
    // Daily: at most 5 USDC per UTC day to this payee.
    GOTHERPAYEE: { dailyCap: "50000000" },
    // Rolling window: at most 1 USDC in any hour to this payee.
    GTHIRDPAYEE: { window: { windowSeconds: 3600, cap: "10000000" } },
  },
  perResource: {
    // Exact: this one route, lifetime.
    "/api/report": { cap: "20000000" },
    // Prefix, daily: every route under /api/quotes/.
    "/api/quotes/": { match: "prefix", dailyCap: "10000000" },
    // Prefix, rolling window: every route under /api/, 2 USDC per 10 minutes.
    // It also applies to /api/report and /api/quotes/*, on top of their own caps.
    "/api/": { match: "prefix", window: { windowSeconds: 600, cap: "20000000" } },
  },
};
```

USDC on Stellar has 7 decimals, so `10000000` is 1 USDC.

**`rateLimit`** caps how often the agent pays. It answers three questions.

- **Over which windows.** `windows` lists one or more sliding windows, and a payment must fit in every one of them. An event counts while it is at most `windowSeconds` old: one recorded at 12:00:00 still counts at 12:01:00 against a 60 second window, and stops counting a millisecond later. `requestsPerMinute: 30` is shorthand for `windows: [{ windowSeconds: 60, limit: 30 }]`. Set one or the other, not both.
- **What is counted.** With `count: "settlements"`, the default, a payment counts when it is recorded after it settles, so failed and blocked payments never count. With `count: "attempts"`, a payment counts at the moment the client sends it, whether or not it then settles, and each retry with a fresh authorization counts again. A payment the policy blocked is not an attempt and is not counted. The client counts an attempt through the engine's `admit`, which evaluates and counts in one step, so of several concurrent attempts only as many pass as there are free slots. Evaluating, `check`, a shadow comparison or a dry run never counts anything.
- **Per whom.** With `scope: "global"`, the default, every payment shares one count. With `scope: "per-counterparty"`, each payee address has its own count, the same key `perService` uses, and the decision detail names the payee. At most `perCounterpartyKeyLimit` payees (default 1024) are tracked. A payee whose events have all left every window is idle and is dropped first. When every tracked payee is still active, a payment to a new payee is refused until one goes idle: dropping an active payee would reset its count and let it through.

The count is exact: each tracked key keeps the timestamps of its newest events, never more than the largest limit, so memory is bounded and no approximation is involved. The rate limit has its own windows, independent of the one-minute window the anomaly stop uses.

A worked example: an agent that may make 60 payment attempts a minute and 1000 an hour to each service, however the payments turn out.

```ts
const policy: Policy = {
  policyVersion: 1,
  rateLimit: {
    windows: [
      { windowSeconds: 60, limit: 60 },
      { windowSeconds: 3600, limit: 1000 },
    ],
    count: "attempts",
    scope: "per-counterparty",
  },
};
```

After 1000 attempts to `GQUOTES` in the last hour, the next one is blocked with the hourly window in the trace, even if the last minute was quiet:

```text
per-counterparty rate limit for GQUOTES exceeded: 1000 attempts in the last 3600 seconds, limit 1000
```

A payment to `GWEATHER` in the same hour is still allowed, because each payee has its own count. With the default `scope: "global"`, it would be blocked too.

**`anomaly.maxSpendPerMinute`** is the per-minute spend ceiling. Crossing it trips the anomaly stop, which the agent surfaces as a hard error: a sudden burst of spending is the most common signal of a compromised key or a runaway agent, and the engine fails closed rather than rationalize the spike.

**`anomaly.adaptive`** adds an EWMA (exponentially weighted moving average) of committed spend in completed one-minute buckets, plus an EWMA of the absolute deviation from that baseline. The observed rate blocks when it is above `baseline + sensitivity * deviation`. `smoothing` and `sensitivity` are positive rational values represented as integer strings, so amounts and decisions stay deterministic and float-free. The default scope is per asset; `asset-payee` gives each counterparty its own baseline. The rule never blocks during `warmupPeriods`, and only `record()` calls train it, so rejected attempts cannot raise the baseline.

Set `maxBaselineGrowthPerMinute` to cap how much the baseline can rise when a new bucket is learned. This prevents a slow or sustained ramp from ratcheting the detector upward without bound. The cap can also make a legitimate step-up produce alerts until the operator changes the policy. The adaptive rule is application-layer defense in depth: it is stateful and must be persisted through the policy-state seam when multiple processes share one policy.

## Two layers of enforcement

Where the agent uses an OpenZeppelin smart account, Tollway maps as many constraints as possible down to the on-chain smart-account policy, so the chain itself backs the limit. Where it does not, Tollway enforces at the application layer. Defense in depth, with the honest caveat that application-layer enforcement is only as strong as the process running it.

## In the code

The policy types and the in-memory engine live in `packages/core/src/policy.ts`:

```ts
import { createPolicyEngine, type Policy } from "@vegaforge/tollway-core";

const engine = createPolicyEngine({
  policyVersion: 1,
  budgets: { daily: "1000000000" },
  perModel: { "mpp-channel": { minChannelDeposit: "500000000" } },
});

const decision = await engine.check(intent);
if (!decision.allowed) {
  console.warn(`policy blocked: ${decision.rule} - ${decision.detail}`);
}
```

After a settlement lands, the agent calls `engine.record(intent)` so daily and per-service totals advance.

## Channel opens and headroom

A channel locks its deposit when it opens, and the deposit is not spent until a payment draws it down. The policy engine checks the deposit at open time, through two calls:

- `engine.headroom(asset, payee)` returns what the policy still allows for one asset and payee, as an integer string. It is the smallest remaining amount across the daily budget, the total budget, and the payee's per-service lifetime cap, `dailyCap` and rolling `window`. `limitedBy` names the ceiling that sets it, and both fields are `null` when no ceiling applies.
- `engine.evaluateChannelOpen({ payee, asset, deposit })` checks the deposit against `minChannelDeposit` and against that headroom. It returns `allowed`, `wouldBlock`, the `rule` that blocks (or `null`), and a `detail` for logs. It does not record spend. A deposit is not spend: unspent funds return to the funder when the channel closes.

`minChannelDeposit` applies only to channel opens. A per-request channel payment is never compared with it. Earlier releases compared every channel payment's price with the minimum, which blocked each channel payment priced below it and never checked a deposit. `sizeDeposit` in `@vegaforge/tollway-channels` uses `headroom` to choose the deposit.

## Decision traces

`engine.evaluate(intent)` returns a decision trace: one entry for every rule, whether it applied or not, with the numbers it compared. `engine.check(intent)` is built on it. It evaluates the trace and reports the first failing entry, so the decision and its explanation cannot disagree. The client uses the same derivation (`decisionFromTrace`, exported from `@vegaforge/tollway-core`).

Rules are evaluated in this order. Static checks on the payment come first, then the stateful ceilings. Every rule runs even after one fails, so the trace is always complete; the decision names the first failure in this order.

| Order | `id` | `rule` (what `check()` reports) | Window |
| ----- | ---- | ------------------------------- | ------ |
| 1 | `per-model-disabled` | `per-model-disabled` | none |
| 2 | `min-channel-deposit` | `min-channel-deposit` | none |
| 3 | `budget-daily` | `budget` | `utc-day` |
| 4 | `budget-total` | `budget` | `lifetime` |
| 5 | `per-service` | `per-service` | `lifetime` |
| 6 | `per-service-daily` | `per-service-daily` | `utc-day` |
| 7 | `per-service-window` | `per-service-window` | `sliding`, configurable |
| 8 | `per-resource` | `per-resource` | `lifetime` |
| 9 | `per-resource-daily` | `per-resource-daily` | `utc-day` |
| 10 | `per-resource-window` | `per-resource-window` | `sliding`, configurable |
| 11 | `rate-limit` | `rate-limit` | `sliding`, 60 seconds |
| 12 | `anomaly` | `anomaly` | `sliding`, 60 seconds |
| 13 | `anomaly-adaptive` | `anomaly-adaptive` | `sliding`, 60 seconds |

Both budget rules report `budget` to `check()` and `PolicyBlockedError`, as they always have. The trace keeps them apart with `id`.

What the fields mean:

- **`version`** is the shape version, currently `1`. A consumer that stores traces should parse them with `policyTraceSchema` from `@vegaforge/tollway-core`, which rejects any other version and any trace whose summary contradicts its entries.
- **`allowed`** is the decision after the mode is applied. It is always `true` in dry-run.
- **`wouldBlock`** is `true` when any entry failed, whatever the mode. **`blockedBy`** is the `id` of the first failing entry, or `null`.
- **`configured`** says whether the policy sets the rule at all. A rule can be configured and still `not-applicable` to this payment: a cap for another payee, or a channel minimum on an x402 payment.
- **`outcome`** is `pass`, `fail`, or `not-applicable`.
- **`limit`**, **`current`** and **`projected`** are integer strings. `current` is the counter before this payment and `projected` is what the limit is compared with if it goes through. For amounts these are in the asset's smallest unit; for `rate-limit` they are request counts. A rule that keeps no counter has `current: null`, and a rule with no numeric limit (a disabled model) has `limit: null`.
- **`window`** is the period the counter covers: `{ "kind": "utc-day", "day": "YYYY-MM-DD" }`, `{ "kind": "lifetime" }`, or `{ "kind": "sliding", "seconds": 60 }`. Static rules have `null`.
- **`intent`** holds the payee, resource, amount, asset, and model. A trace never carries request bodies or headers.

`evaluate` does not record spend. Call `record` after the payment settles, as before.

## Dry-run and shadow policies

The client emits the active policy's trace as a `policy:decision` event before it pays or blocks:

```ts
import { createPolicyEngine } from "@vegaforge/tollway-core";
import { createClient } from "@vegaforge/tollway-client";

const client = createClient({
  network: "testnet",
  settler,
  policy: createPolicyEngine(activePolicy),
  // The candidate is evaluated next to the active policy and never blocks.
  shadow: createPolicyEngine(candidatePolicy),
});

client.on((event) => {
  if (event.type === "policy:decision" && event.trace.wouldBlock) {
    log.info("policy decision", event.trace);
  }
  if (event.type === "policy:shadow" && !event.comparison.sameDecision) {
    log.info("candidate policy disagrees", event.comparison.differences);
  }
  if (event.type === "policy:shadow-error") {
    log.warn("candidate policy failed to evaluate", event.error);
  }
});
```

- **Shadow.** A `shadow` engine is evaluated on every payment next to the active policy. The client emits `policy:shadow` with both traces and a comparison: whether the two would decide alike, and each rule whose outcome differs. Modes are ignored in the comparison: it asks what each policy would do if enforced. The shadow never affects the payment, and if its `evaluate` throws (a custom engine over a policy source that is not validated, say) the client emits `policy:shadow-error` and pays as usual. Settled payments are recorded on the shadow too, so its budgets count real spend from the moment the client is created. With no active `policy`, the candidate is compared with no policy at all.
- **Dry-run.** With `mode: "dry-run"` the active policy evaluates and records exactly as in enforce mode, but allows every payment. The `policy:decision` trace marks the would-be block with `wouldBlock` and `blockedBy`. Dry-run is never the default, and the client logs a warning through `console.warn` (or the `logger` option) when it is created with a dry-run policy.

The trace and the shadow comparison are only built into events while at least one handler is registered; with none, shadow evaluation is skipped and only its spend is recorded.

### Rollout recipe

To replace a policy without finding out from failed payments:

1. **Shadow.** Keep the current policy as `policy` and pass the new one as `shadow`. Watch `policy:shadow` events where `sameDecision` is `false` until the differences are the ones you intended.
2. **Dry-run.** Make the new policy the active one with `mode: "dry-run"`. Payments go through; `policy:decision` events with `wouldBlock: true` show exactly what it would stop, with the numbers. Spend is recorded, so the budgets it reports are real.
3. **Enforce.** Remove `mode` (or set `"enforce"`). The warning at startup goes away and failing rules block payments with `PolicyBlockedError`.

Creating a new engine starts its counters at zero. If an engine is replaced mid-day, its daily budget does not know about spend recorded by the old one.
