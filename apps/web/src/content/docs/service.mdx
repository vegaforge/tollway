`@vegaforge/tollway-service` is an optional HTTP service over Tollway telemetry. Gates and clients POST the `PaymentMetric` values they already record, and a dashboard reads spend summaries, bucketed time series and JSON or CSV exports. It exists for the case an in-process hub cannot serve: many gates and agents in different processes reporting to one place.

The service holds no receipt signing key, signs nothing, and makes no outbound call. It cannot move a payment. It is a read and write surface over telemetry.

```ts
import { createService, hashApiKey } from "@vegaforge/tollway-service";

const app = createService({
  apiKeys: [
    { id: "gateways", keyHash: await hashApiKey(process.env.METRICS_INGEST_KEY!), scopes: ["ingest"] },
    { id: "dashboard", keyHash: await hashApiKey(process.env.METRICS_READ_KEY!), scopes: ["read"] },
  ],
});
```

`createService` returns a [Hono](https://hono.dev) app. Serve it with the Hono adapter for your runtime; the service package itself does not open a socket.

## Authentication and scopes

Every metrics route needs `Authorization: Bearer <key>`. Keys are configured as SHA-256 hex digests, never as the secret, so a leaked configuration does not hand over a working key. Compare the digest at verification with WebCrypto; `hashApiKey(key)` produces the value to store.

| Scope | Routes |
| ----- | ------ |
| `ingest` | `POST /v1/metrics` |
| `read` | `GET /v1/metrics/summary`, `/v1/metrics/series`, `/v1/metrics/export` |

A missing or unknown key is `401`. A valid key without the scope the route needs is `403`. The health and OpenAPI routes are public.

## Ingest

```http
POST /v1/metrics
Authorization: Bearer <ingest key>
Content-Type: application/json

{
  "metrics": [
    {
      "payer": "GAGENT...",
      "payee": "GSERVICE...",
      "model": "x402",
      "amount": "10000",
      "asset": "USDC:GA5Z...",
      "latencyMs": 182,
      "outcome": "settled",
      "at": "2026-11-23T10:04:31.000Z"
    }
  ]
}
```

The body is validated field by field with a zod schema that mirrors `PaymentMetric`: `amount` must be an integer string in the asset's smallest unit, `at` must be ISO 8601 with a zone, and `latencyMs` must be a finite non-negative number. A batch holds 1 to 1000 metrics and is answered with `202 {"accepted": n}` after the store has accepted it.

## Summary

```http
GET /v1/metrics/summary?asset=USDC:GA5Z...&outcome=settled&from=2026-11-01T00:00:00Z&to=2026-11-24T00:00:00Z
```

Available filters are `payer`, `payee`, `model`, `asset`, `outcome`, `from` and `to`. An unknown query parameter is a `400`, so a typo cannot silently widen a query.

The response carries `count` (every matched metric), `byOutcome` (`settled`, `failed`, `skipped`) and per-asset totals:

```json
{
  "count": 5,
  "byOutcome": { "settled": 3, "failed": 1, "skipped": 1 },
  "byAsset": [{ "asset": "USDC:GA5Z...", "amount": "1250", "count": 2 }],
  "byModel": [{ "model": "x402", "asset": "USDC:GA5Z...", "amount": "1000", "count": 1 }],
  "byPayer": [{ "payer": "GAGENT...", "asset": "USDC:GA5Z...", "amount": "1000", "count": 1 }],
  "byPayee": [{ "payee": "GSERVICE...", "asset": "USDC:GA5Z...", "amount": "1000", "count": 1 }]
}
```

Only settled metrics add to an amount, and amounts in different assets are never added, so the response has no cross-asset total. A failure rate is `byOutcome.failed / count`.

## Time series

```http
GET /v1/metrics/series?from=2026-11-23T00:00:00Z&to=2026-11-24T00:00:00Z&bucket=1h&groupBy=model
```

`bucket` is `1m`, `1h` or `1d`. `groupBy` is `model` (the default), `payer` or `payee`; every row is always per asset. The range is `[from, to)`, both ends are required, and every bucket in the range is returned, empty ones included. Each row carries the settled `amount`, the `settled`, `failed` and `skipped` counts, and nearest-rank `latencyMs` percentiles (`p50`, `p95`, `p99`, or `null` for an empty row). The filters are the same as the summary's.

A range wider than `maxRangeMs` (default 90 days), or one that would produce more buckets or rows than the observability hub allows, is refused with `400` and the limit that was hit, so a dashboard query cannot exhaust the process.

## Export

```http
GET /v1/metrics/export?format=json&from=2026-11-01T00:00:00Z
```

`format` is `json` or `csv`, and the filters are the summary's. The response is the same serialization `hub.export` produces, with `Content-Type: application/json` or `text/csv` and a `Content-Disposition: attachment` filename. CSV cells that could be read as a spreadsheet formula are prefixed with a single quote, as in the hub. An export larger than `maxExportRows` (default 10 000) is refused with `400` and the limit.

## Errors

Every failure has one shape:

```json
{ "error": { "code": "range-too-large", "message": "the range is wider than the limit of 7776000000 ms", "limit": { "name": "maxRangeMs", "value": 7776000000 } } }
```

`details` carries field-level messages for a validation failure. A request that fails validation is `400`. An unexpected failure is reported to the `onError` hook (default `console.error`) and answered with `500` and a generic message, so an internal path or stack trace never reaches a caller.

## Storage

By default the service records into an in-memory observability hub, so its history is process-local and a restart starts empty. `createService({ store })` accepts any `MetricsStore`; the rollups stay the observability hub's, so a persistent store (tracked in [#217](https://github.com/vegaforge/tollway/issues/217)) replaces storage without changing a route. Multiple service processes need a shared store to answer the same question the same way.

## OpenAPI

`GET /openapi.json` serves an OpenAPI 3.1 document with every route, its parameters, and the request and response schemas, including the `bearerAuth` scheme. Point a generated client or a docs viewer at it.
