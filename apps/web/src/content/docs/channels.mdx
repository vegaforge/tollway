Channel mode is the right answer when one agent hits one service often enough that paying per request would dominate the on-chain footprint. A one-way payment channel lives in a Soroban contract; the funder deposits once, then makes many off-chain payments by signing cumulative commitments. Closing the channel submits one transaction that transfers the cumulative committed amount to the recipient and returns the remainder to the funder.

The raw `@stellar/mpp` SDK gives you the primitive. Tollway runs the lifecycle.

## The four phases

**Open.** Deposit into the one-way channel contract, sized from the agent's budget and predicted demand. The open transaction is the only required on-chain settlement until close.

**Commit.** For each paid interaction, produce and store the next cumulative commitment, advancing the off-chain counter with no on-chain transaction. The commitment is the agent's signature over the new cumulative total plus a monotonically increasing sequence number; replaying an older commitment is a no-op because the contract only honors the highest one at close.

**Close.** Decide timing from heuristics: budget nearly drawn down, idle timeout reached, end-of-session signal received. Submit the single settlement, which transfers the latest committed amount to the recipient and returns the remainder to the funder.

A close can be interrupted: the process dies, or the network call times out after the transaction went out. So before submitting, the manager records the attempt on the channel (an id, the ledger it started at, and the time) and moves the channel to `closing`. If the close fails in a way that may have reached the chain, the channel stays `closing`. It goes back to `open` only when the adapter reports that nothing was submitted, with `CloseNotSubmittedError`. A settlement that differs from the last commitment moves the channel to `settlement-mismatched`, which is terminal: the channel never takes another commit.

`resume(channelId)` finishes a `closing` channel from what the chain says. If no close is on chain, it closes again. If the contract is closed and empty, it finds the settlement transaction and marks the channel `closed` with its hash and remainder. If the contract is closed with funds still in it, a funder-started close or a dispute, it hands the channel to recovery as `recovering`. When the chain says closed but no settlement can be found, or the RPC no longer keeps events back to the attempt, `resume` throws and the channel stays `closing` for an operator. `resumeAll()` does this for every `closing` channel, typically at startup, and reports each result without stopping at the first error.

```ts
const manager = createChannelManager({ adapter, store });
for (const outcome of (await manager.resumeAll()).outcomes) {
  if (outcome.kind === "error") console.error(`resume ${outcome.channelId} failed`, outcome.error);
}
```

Repeated and concurrent calls in one process submit at most one close. Two processes resuming over a shared store can both submit until the store supports compare-and-set ([#175](https://github.com/vegaforge/tollway/issues/175)), so resume from one process until then.

**Recover.** If the counterparty stops responding mid-channel, follow the contract's dispute or timeout path to get the committed funds back. This event is surfaced loudly: silent recovery is the worst failure mode for channel mode.

Recovery is a first-class feature here, not an afterthought. The edge cases live in that path, and so do the tests.

## Why the order matters

Per the design notes, channel mode is naturally idempotent: a repeated commitment at the same sequence is a no-op. Tollway enforces that property at the commit step so a retry storm does not double-commit.

## In the code

The lifecycle manager lives in `packages/channels/src/`. Open, commit, close and resume are implemented against an injected `MppChannelAdapter`, and `createStellarMppChannelAdapter` backs it with `@stellar/mpp` 0.7.1. Recover throws `NotImplementedError` today ([#38](https://github.com/vegaforge/tollway/issues/38)). `@stellar/mpp/channel/server` exposes `close`, `getChannelState` and `watchChannel`; it has no `close_start` or `refund` helper, which recovery needs. The adapter finds a settlement in the channel contract's events: the transaction whose `close` event is effective at its own ledger, with its `withdraw` and `refund` amounts.

## Lifecycle events

Opening a channel locks funds and closing it releases them, so the manager reports both. Pass `onEvent` to `createChannelManager`:

```ts
import { createChannelManager, toObservabilitySink } from "@vegaforge/tollway-channels";

const bridge = toObservabilitySink(hub, {
  onDeliveryError: (error, event) => log.warn({ error, event }, "channel webhook failed"),
});
const manager = createChannelManager({
  adapter,
  onEvent: bridge.onEvent,
  onEventError: (error, event) => log.warn({ error, event }, "channel observer failed"),
});

// On shutdown, wait for webhook deliveries still in flight.
await bridge.flush();
```

| Event | When | Fields besides `at`, `channelId`, `counterparty`, `asset`, `network` |
| --- | --- | --- |
| `channel:opened` | The open landed and the channel was stored. | `deposit`, `openTxHash` |
| `channel:closing` | A close was recorded as started, before it is submitted. | `cumulativeAmount` |
| `channel:closed` | The close settled and was stored. | `settlementTxHash`, `settledAmount`, `returnedRemainder` |
| `channel:close-failed` | The close did not complete. | `status` (`open`, `closing` or `settlement-mismatched`), `error` |

Each event is emitted only after its store write succeeds. `at` comes from the manager's `now`, and amounts are integer strings in the asset's smallest unit. The handler is not awaited: a handler that throws or rejects never changes the result of `open` or `close`, and its error goes to `onEventError`.

`toObservabilitySink(hub)` forwards `channel:opened` and `channel:closed` as the `channel.opened` and `channel.closed` webhooks; the other events are not webhooks. It takes any object with the hub's `emit`, so this package does not depend on `@vegaforge/tollway-observability`.

A channel settler on the client side puts the same events on the client's `on()` stream through `ClientSettler.subscribe`.
