# Contributing to Tollway

Thank you for your interest in contributing. Tollway is a pnpm monorepo designed so that contributors can pick up one package without building the world. Each adapter, each example, the dashboard widgets, and the reconciliation engine are independent, well-scoped pieces you can own without deep context.

The full rulebook, for people and for coding agents, is [AGENTS.md](AGENTS.md). The architecture rules and the payment-path defect checklist are in [`.claude/skills/tollway-engineering-standards/SKILL.md`](.claude/skills/tollway-engineering-standards/SKILL.md). This page is the short version.

## Prerequisites

- Node 22 or later
- pnpm 10 or later (`corepack enable` or `npm i -g pnpm`)

## Getting started

```bash
git clone https://github.com/vegaforge/tollway.git
cd tollway
pnpm install
./scripts/preflight.sh
```

`pnpm install` also installs two Git hooks through [lefthook](https://lefthook.dev):

- **pre-commit** runs Biome on the files you staged and re-stages its fixes.
- **pre-push** runs `./scripts/preflight.sh --fast`: everything except the build.

If the hooks are missing (for example, you installed with scripts disabled), run `pnpm exec lefthook install`.

Useful commands:

| Command | What it does |
| ------- | ------------ |
| `./scripts/preflight.sh` | Run all five gates: format check, lint, typecheck, tests, build |
| `./scripts/preflight.sh --fast` | The same, without the build |
| `pnpm build` | Build all packages through Turborepo |
| `pnpm test` | Run all Vitest suites |
| `pnpm typecheck` | Typecheck all packages |
| `pnpm lint` | Biome lint and format check; warnings fail |
| `pnpm mutation` | Full Stryker mutation run on `@vegaforge/tollway-core` and `@vegaforge/tollway-server`. Slow; `pnpm test` and `preflight.sh` never run it. Reports land in `packages/<name>/reports/mutation/` |
| `pnpm mutation:incremental` | Re-test only the mutants changed since the last run's report, as CI does on a pull request |
| `pnpm format:check` | Biome format check only |
| `pnpm lint:fix` | Apply Biome fixes |
| `pnpm --filter @vegaforge/tollway-core test` | Run one package's tests |
| `pnpm --filter @vegaforge/tollway-integration-tests test` | Pay real transactions on a local Stellar network; needs Docker, see [docs/local-network-tests.md](docs/local-network-tests.md) |

## Where to start

- Browse the [open issues](https://github.com/vegaforge/tollway/issues). Each is scoped to a package, carries acceptance criteria, and notes any prerequisite it depends on.
- Issues labeled [`difficulty:good-first-issue`](https://github.com/vegaforge/tollway/issues?q=is%3Aissue+is%3Aopen+label%3Adifficulty%3Agood-first-issue) are the friendliest starting points, biased toward the framework adapters and example apps.
- The [design document](docs/design.md) is the source of truth for architecture and scope. Stub code carries TODO comments pointing at the relevant section.

## Project conventions

- TypeScript strict mode everywhere. No `any` in `@vegaforge/tollway-core`.
- Lint and format with Biome. Run `pnpm lint:fix` before pushing.
- Tests with Vitest. New behavior needs a test.
- Library packages build with tsup (ESM, CJS, and type declarations).
- Do not invent x402 or MPP API surfaces. Where the exact SDK call is unknown, keep a typed interface and a TODO pointing at the upstream docs.
- Tollway never custodies funds. Changes that would make Tollway hold value will not be accepted. See the [security model](docs/design.md#security-model).
- Exported functions, types and constants carry a TSDoc comment. The docs site's API reference is generated from them.

## Previewing the API reference

The reference under `/docs/api` is generated by TypeDoc from each publishable package's `src/`, so it is not committed (`apps/web/src/content/docs/api/` is gitignored). To preview it:

```bash
pnpm --filter @vegaforge/tollway-web run api   # generate the pages and check every package has one
pnpm --filter @vegaforge/tollway-web dev       # regenerates, then serves http://localhost:3000/docs/api
```

`run api` fails on a broken `{@link}` or on a public type that references something its package does not export, and it prints the exports that still have no doc comment. The dev server does not regenerate on later source edits; run `run api` again.

## Public API reports

Each publishable package commits an API report at `packages/<name>/etc/<name>.api.md`, generated by API Extractor from the built type declarations. CI fails when the built API no longer matches the committed report.

**A change to a report is a change to the public API.** Agree it with the maintainer in the issue thread before you code it; the maintainer records it in an ADR. Do not regenerate a report just to make CI pass.

When the change is agreed, update the reports after a build:

```bash
pnpm build
bash scripts/check-api-reports.sh --update   # rewrites packages/*/etc/*.api.md
```

Three more checks guard what a consumer installs, and both preflight (after the build) and the CI `build` job run all of them:

- `scripts/check-package-exports.sh` runs publint and arethetypeswrong (`--profile node16`) on each packed tarball. Two entry points are excluded from arethetypeswrong because they carry no types by design: the theme's `./tokens.css` and core's `./schema/policy.schema.json`. publint still checks that both files exist. The `node10` column fails for subpath exports (`./proxy`, `./sqlite`, `./policy-loader`, `./preset`) because `node10` resolution predates export maps; the node16 profile ignores it.
- `scripts/check-package-consumers.sh` installs every tarball into a fresh project, then type-checks an ESM and a CommonJS consumer under `moduleResolution: node16` and loads every entry point both ways.
- `scripts/check-api-reports.sh` is the report check above.

Packages are published from `release.yml` with npm provenance. To check that an installed version was built and published by this repository's workflow, run `npm audit signatures` in a project that depends on it, or open the version's page on npmjs.com and look for the provenance panel.

## Before you push

> - Run `./scripts/preflight.sh`. Format, lint, types, tests and build must all pass.
> - A pull request may close up to four issues, and you must be assigned to every one. The body closes each: `Closes #<number>` on its own line.
> - Open the pull request against `dev`.
> - Do not touch CI, scripts, `package.json`, lockfiles or `*.config.*` files unless the issue asks you to.
> - Do not mark an ADR as Accepted. Only the maintainer approves a design.

## Pull request workflow

1. Comment on the issue and wait to be assigned. Pull requests for issues you are not assigned to are closed without review.
2. Fork the repository and create a branch from an up-to-date `dev` (for example `feat/adapter-hono-middleware`).
3. For a bug, write the failing test first, then the fix.
4. If the change touches `packages/*/src` or `apps/*/src`, add a release note: copy `docs/release-notes/TEMPLATE.md` to `docs/release-notes/<YYYY-MM-DD>-<topic>.md`. CI fails without it.
5. If the change affects a publishable package, also add a changeset: `pnpm changeset`. The release note is the human summary; the changeset is the version bump.
6. Run `./scripts/preflight.sh`. All five gates must pass.
7. Open a pull request **into `dev`** using the template. The body must include `Closes #<issue>`.

Each issue is the design the maintainer already approved, so you do not write an ADR or a plan for it. If you want to build it differently from what the issue describes, propose that in the issue thread and wait for the maintainer to agree before coding it. Only the maintainer marks a design (ADR) as Accepted. See "Contributors" in [AGENTS.md](AGENTS.md).

When you open the pull request, a `contribution rules` check confirms that it closes between one and four issues, that you are assigned to each of them, and that no ADR is marked Accepted. It runs first and tells you in plain words what to change.

Commit messages follow Conventional Commits, for example `feat(channels): add idle-timeout close heuristic`.

## Branches and environments

```text
feature branch --squash--> dev --merge--> staging --merge--> main
```

| Branch    | Purpose                                         | Accepts pull requests from | Who merges     |
| --------- | ----------------------------------------------- | -------------------------- | -------------- |
| `dev`     | Development. Every contribution lands here.     | feature branches and forks | the maintainer |
| `staging` | Testing. `dev` is promoted here when ready.     | `dev` only                 | the maintainer |
| `main`    | Production. `staging` is promoted when tested.  | `staging` only             | the maintainer |

- `dev` is the default branch. Open every pull request against it, including
  urgent fixes. There is no shortcut into `staging` or `main`.
- The `branch flow` job inside the required `quality` check rejects a pull
  request into `staging` that is not from `dev`, one into `main` that is not
  from `staging`, and any pull request into `staging` or `main` from a fork.
- Nothing merges while a check is red, and only the maintainer can merge into
  any of the three branches.
- Contributions are squash-merged into `dev`. Promotions use a merge commit so
  the three branches keep a shared history.
- Package versions are bumped on `dev` through the Changesets "Version
  Packages" pull request, which the maintainer starts by hand, and published
  by hand from `main`. Neither happens automatically.

The decision is recorded in
[ADR-2026-11-18-branch-flow](docs/adr/ADR-2026-11-18-branch-flow.md).

## When CI fails or does not run

| What you see | Why | What to do |
| --- | --- | --- |
| No checks at all on your pull request | Your branch conflicts with `dev`, so GitHub cannot test it, or your GitHub account is brand new and the first run waits for the maintainer | Merge the latest `dev` into your branch and resolve the conflicts. If there are none, wait for the maintainer to approve the run |
| `ERR_PNPM_OUTDATED_LOCKFILE`, or "Lockfile out of date" | A `package.json` changed without `pnpm-lock.yaml`, often because the branch was cut from an old `dev` | Merge the latest `dev`, run `pnpm install`, commit `pnpm-lock.yaml`. Keep the versions `dev` already has |
| `contribution rules` | The pull request closes no issue or more than four, closes one you are not assigned to, or marks an ADR as Accepted | Follow the message: fix the `Closes #N` lines, get assigned on Drips, or set the ADR to `Proposed, awaiting maintainer approval` |
| `maintainer review` | You changed a file that can run code (CI, scripts, `package.json`, lockfile, `*.config.*`) | Nothing. It turns green when the maintainer approves your latest commit |
| `malicious patterns`: "could not be analysed" | Semgrep's parser could not read a line of valid code | Rewrite that line in a simpler form; the message names the line and gives an example |
| `format, lint, typecheck` | Formatting, lint or type errors | Run `./scripts/preflight.sh` locally before pushing; `pnpm lint:fix` fixes most of them |
| `tests` or `build, release notes` | A failing test, a build error, or a source change without a release note | Run `./scripts/preflight.sh`; add a release note under `docs/release-notes/` |

`./scripts/preflight.sh` runs the same gates as CI. If it passes locally on a branch that is up to date with `dev`, CI passes too, apart from `maintainer review`.

## Security checks on pull requests

Every pull request runs a `security` check next to `quality`. It reads your
changes without installing or running them, and it fails when it finds:

- compiled or archived files (executables, native modules, zip or tar files);
  images and fonts are fine inside the asset folders in
  `.github/security/allowed-binaries.txt`
- invisible Unicode characters, minified or encoded code, or source files over
  512 KB
- SVGs with scripts, event handlers, embedded HTML or links to outside files
- dependencies from anywhere other than the official registries, known
  malicious packages, or new known vulnerabilities
- new install-time scripts (`preinstall`, `postinstall`, `prepare`)
- code that reads credential files, sends environment secrets over the network,
  or downloads and runs code
- workflow changes with unsafe triggers or permissions, and known malware
  signatures
- editor tasks that run on folder open (`"runOn": "folderOpen"`) or settings
  that allow automatic tasks
- files named as fonts or images whose content is something else, `.lik`
  files, and vendored `fa-solid*` or `fa-regular*` font files
- anything committed under a `dist/` or `build/` directory
- `start`, `dev`, `build`, `test`, `serve` or `preview` scripts that run a
  loose `.js` file with `node` (files under `scripts/` are fine)
- code pushed out of view after a long run of spaces or tabs
- strings known to appear in Wave malware

These last checks were added after Drips warned Wave maintainers about
malicious pull requests. No approval overrides them.

Changes to build scripts, Git hooks, workflows, dependency manifests and other
files that run code (the list is in `.github/security/sensitive-paths.txt`) also
wait for a maintainer to review and approve your latest commit. The
`maintainer review` check shows that wait; it is not a problem with your code. Pushing again
after that approval asks for a new review. This is expected, so leave those
files out of your pull request unless the issue asks for them.

If you think the check is wrong about your change, say so in the pull request.
A maintainer will look at it and, if needed, narrow the rule. Do not try to work
around a finding.
